# FDE 客户档案后续开发 SOP

本 SOP 把 M0–M6 验证结果固化为后续开发、采集、审阅和上线的统一作业方法。目标定义仍以 `GOAL.md` 为准；SOP 只说明怎样稳定复现已经验证过的结果，不扩展产品范围。

## 1. 完成定义

一次客户档案作业只有同时满足以下条件才算完成：

1. 客户主体已用统一社会信用代码或股票代码确认，不按品牌名猜主体。
2. 采集器按来源独立运行；单一来源失败不阻断其他来源。
3. 每个非空字段都有一条 `Fact` 指向 `Source`，并保留页码或原文片段。
4. `Industry` 与 `IndustryTerm` 按行业复用，不为每家公司复制一份。
5. 第 9 章每个机会同时指向具体 `ProcessStep` 与 `SystemInUse`。
6. 第 10 章每个问题都有前 8 章的事实依据，问题总数不超过 10 条。
7. HTML 包含第 1–10 章；第二次及以后生成时包含第 0 章真实变化。
8. 文字、来源覆盖、数值一致性与重复写入检查全部通过。
9. 生产刷新不覆盖历史 `DossierRun`、周报选择或 SQLite volume。

## 2. 角色与责任

| 角色 | 必须负责 | 不得代替谁做决定 | 交付证据 |
|---|---|---|---|
| FDE | 选客户、确认主体、审阅机会、选择周报有用信息、核对进场问题 | 不代替数据开发补来源 | 主体确认、M0 手写档案、周报选择时间、验收意见 |
| 研究负责人 | 维护来源清单、确认原始页面、处理同字段冲突 | 不凭搜索摘要写字段 | 来源 URL、发布日期、页码或原文片段 |
| 数据开发 | 编写采集器、抽取器、合并和 SQLite 写入 | 不自行判断业务机会优先级 | fixture、字段映射、`Source`/`Fact` 行、失败日志 |
| 后端开发 | 固定 schema、事务、档案刷新、周报和权限接口 | 不绕过来源约束直接写库 | API 测试、数据库迁移、持久化验证 |
| 前端开发 | 0–10 章、组织树、系统地图、时间线、表格和打印版 | 不把缺失数据显示成结论 | 可打开 HTML、文字上限检查、可点击来源 |
| 审阅人 | 抽查来源、页码、字段覆盖、机会与问题依据 | 不接受“测试通过”替代人工抽查 | A1–A9 记录、失败项和复查结果 |
| 生产维护 | 镜像、volume、环境变量、Cron、健康检查和回滚 | 不改写 FDE 的历史选择时间 | 镜像摘要、上线时间、健康检查、四周进度 |

同一个人可以承担多个角色，但每个交付证据仍须分别存在。

## 3. 单个客户档案作业表

| 顺序 | 任务 | 输入 | 操作 | 输出 | 完成条件 | 失败时处理 |
|---|---|---|---|---|---|---|
| 1 | 选择客户 | 目标客户名单或手动输入 | 确认法定名称、信用代码/股票代码、签约主体边界 | `Company.id`、名称、上市状态 | 主键唯一，品牌与法人边界写清 | 停止采集，请 FDE 确认主体 |
| 2 | 绑定行业 | 已确认客户 | 查找现有 `Industry`；没有时才创建 | `Company.industry_id` | 同行业公司引用同一行业行 | 不按公司复制行业资料 |
| 3 | 采集招聘 | 客户官网招聘页或公开 JD | 保存职位、部门、技术词和系统词 | `JobPosting`、候选 `OrgUnit`/`SystemInUse` | 每个字段有同页片段 | 页面不可访问则记失败，不猜系统 |
| 4 | 采集招投标 | 政府采购、公共资源或企业采购详情页 | 保存采购方、供应商、系统、金额和日期 | `SystemInUse`、`Event`、`Relationship` | 使用公告详情页，不用搜索摘要 | 搜索页只留候选 URL，不写 schema |
| 5 | 采集年报 | 年报/招股书 PDF | 按页抽行业、业务、流程、财务和高管 | `Industry`、`BusinessLine`、`ProcessStep`、`FinancialSnapshot`、`Position` | 每条抽取保留 PDF 页码和逐字片段 | 页码缺失时整批拒绝写入 |
| 6 | 采集工商 | FDE 提供的工商 CSV | 映射法定主体、实控人与登记字段 | `Company`、`Person`、`Position` | CSV 行可定位，主体主键一致 | 冲突时保留原值并交人工确认 |
| 7 | 采集官网与互动平台 | 官网详情页、官方公众号、互动平台回答 | 抽业务、人物和近两年数字化动作 | `Person`、`Position`、`Event` | 片段包含字段值和发布日期 | 没有明确日期时不冒充最新动作 |
| 8 | 采集厂商与同行 | 已打开的厂商案例/同行公告详情页 | 同时确认客户和厂商/同行后再写关系 | `Relationship`、第 8 章材料 | 搜索结果不直接写入 | 只出现一方名称时保留候选 |
| 9 | 合并 | 各采集器独立输出 | 同字段按 `filing > official > third_party`；同等级取新版本 | 固定 schema | 每个非空字段与 `Fact` 同事务写入 | 缺来源则回滚整批写入 |
| 10 | 生成机会 | 流程、系统、痛点和数据现状 | 只生成同时有流程与系统依据的场景 | `Opportunity` | 每项含流程行、系统行、数据前提和归口部门 | 任一依据缺失则不生成该机会 |
| 11 | 生成进场准备 | 第 1–9 章事实 | 排见人顺序，生成问题和雷区 | 相关方、≤10 个问题、雷区 | 每个问题 `basisIds` 非空 | 无依据的问题删除，不补常识 |
| 12 | 渲染档案 | 完整 schema | 渲染图、表、时间线和可点击来源 | HTML/PDF | 章节齐全且文字上限通过 | 超限直接报错，不自动隐藏内容 |
| 13 | 保存快照 | 本次 schema | 保存 `DossierRun`，与上次快照逐字段对比 | 第 0 章变化 | 相同数据重跑变化为空 | 不按 LLM 措辞差异报变化 |
| 14 | 人工验收 | HTML 与 M0 | FDE 核对事实、机会和问题 | 验收记录 | M4 重合率与问题清单门槛通过 | 记录差异，回到对应采集/生成步骤 |

## 4. 组织树与人物表作业

组织树的目标是帮助 FDE 找到决策链，不是还原一张无法证实的完整公司组织图。

### 4.1 节点建立顺序

1. 先建法定治理和经营层：董事会、董事长、总经理/总裁。
2. 再建年报或官网明确出现的业务单元，每个单元对应业务线或流程。
3. 再建 IT、数据、数字化、AI、信息安全等技术单元。
4. 最后补财务、采购、法务等会影响预算、合同或数据边界的单元。
5. 只有原文明确上下级时才填写 `parent_id`；无法确认时并列展示，不猜层级。
6. 只有原文明确负责人时才填写 `head_person_id`；职务过期时保留结束时间。

### 4.2 每个组织节点的任务表

| 字段 | 必须回答 | 可接受来源 | 不足时怎么写 |
|---|---|---|---|
| 名称 | 公开材料怎样称呼这个部门/业务单元 | 年报、官网、招聘、公开演讲 | 没有正式名称就不建节点 |
| 上级 | 是否有明确汇报或隶属关系 | 年报组织图、官网治理页、正式任命 | 留空并列，不用常见组织结构推断 |
| 负责人 | 谁对该单元负责，事实日期是什么 | 任命公告、年报、官网当前页面 | 留空；人物表可标“负责人待核” |
| 负责内容 | 管哪些业务、流程、系统或数据 | 年报、岗位职责、公开演讲 | 只摘原文覆盖的范围 |
| 对进场的作用 | 能提供什么决策、数据、用户或资源 | 基于已确认职责的工作判断 | 标明“工作判断”，不能写成公司事实 |
| 风险 | 哪些权限、主体或时间仍未确认 | 来源冲突、过期职务、法人边界 | 写成进场问题，不静默合并 |

### 4.3 人物表最低字段

每个人必须展示姓名、当前/历史职务、角色、负责内容、事实日期、来源和一句进场动作。角色只能使用 `决策 / 影响 / 使用 / 阻力 / 待确认`：

- `决策`：有公开证据表明能批准战略、预算、采购或组织资源。
- `影响`：能制定业务/技术路线或影响决策，但未证实最终批准权。
- `使用`：直接拥有流程、系统、数据或试点用户。
- `阻力`：公开职责会对合规、安全、采购或经营风险提出否决条件；不是对个人态度的猜测。
- `待确认`：公开材料不足，必须在 discovery 会核实。

人物变动单独进入时间线；历史职务不得在没有当前来源时显示成现职。

## 5. 来源和联网搜索规则

### 5.1 客户档案主链路

1. 优先招聘、招投标、年报/招股书等结构化来源。
2. 搜索只用于发现演讲、新闻、同行和厂商案例候选，不是主要数据源。
3. 搜索模型返回的摘要永远不直接写 schema；必须打开原链接并保存原文。
4. 招聘 JD 中明确出现的组织、系统与技术栈可按 `official` 使用，不强制寻找第二来源。
5. 法定披露与其他来源冲突时取法定披露；组织和系统类信息中 `official` 与 `filing` 同等可用。

### 5.2 LLM 联网研究通道

Grok、OpenAI、Claude 或兼容中转 API 只负责发现与读取候选。研究通道可以保存正文、指纹、主张和相关查询，并做多来源对照；但它不能绕过客户档案采集器和 `Source`/`Fact` 约束自动写入档案。

### 5.3 行业周报

周报只读取有列表页、可按日期增量处理的中转 JSON。每项必须有 `date`、`kind`、`title`、`summary`、HTTPS 原始来源 URL 和 `sourceType`。搜索摘要、私网 URL、无日期内容和跨行业客户都拒绝写入。

## 6. 开发阶段任务表

| 阶段 | 开发任务 | 必须测试 | 验收输出 | 进入下一阶段前的门槛 |
|---|---|---|---|---|
| M0 | 由 FDE 手写三家已进场客户档案 | 不写自动化代码 | 广联达、世纪互联、北京人力 FESCO 基准 | FDE 确认“进场前看到这个就够了” |
| M1 | 招聘和招投标采集、事务写入 | 每个采集器真实 fixture、缺来源整批拒绝 | `JobPosting`、`SystemInUse`、`OrgUnit` | 第 4/5 章字段命中 ≥70% |
| M2 | 年报 PDF 页级抽取、行业与流程 | 页码、原文、重复抽取一致、错误表格保护 | 第 2/3/7 章 schema | 命中 ≥80%，每条带页码 |
| M3 | 工商 CSV、官网和互动平台 | 主体边界、人物、事件、来源事务 | 第 1/6 章 schema | 命中 ≥80% |
| M4 | 机会、问题、0–10 章、快照 diff | 来源覆盖、文字限制、数值一致、空 diff | 可打开档案 | 机会重合 ≥60%，至少 5 个“当时就该问” |
| M5 | 厂商案例、同行与搜索候选 | 双方名称、详情页、搜索摘要隔离 | 第 8 章 | M0 对标无明显遗漏 |
| M6 | 行业列表 Feed、周报、人工选择写 Event | 去重、同行业、真实选择时间、四周计算 | 一页行业周报 | 代码通过后再开始真实四周验收 |

## 7. A1–A9 检查表

| 标准 | 自动检查 | 人工检查 | 失败处理 |
|---|---|---|---|
| A1 | 生成前非空字段来源覆盖为 100% | 随机点开至少 20 个字段核对页码/片段 | 回到具体采集器修字段映射 |
| A2 | 渲染器统计章节文字并超限报错 | 检查表和图没有把结论藏进长段落 | 改展示结构，不放宽上限 |
| A3 | 记录各采集器和生成步骤耗时 | 用真实外网来源从选客户计时 | 超过 15 分钟先并行采集和减少无效请求 |
| A4 | `Opportunity` 同时有流程和系统行 ID | 逐项打开两类依据 | 缺一类就删除该机会 |
| A5 | 问题数 ≤10 且 `basisIds` 非空 | 核对依据确实回答该问题的来由 | 删除泛化问题或补真实事实 |
| A6 | 两家公司引用相同 `Industry` ID | 对比第二家公司第 2 章 | 删除公司级重复行业行 |
| A7 | 同一输入重复运行数值字段逐项相等 | 抽查金额、人数、比例和年份 | 修抽取排序或非确定性合并 |
| A8 | 无新数据重跑 diff 为空 | 人工确认措辞变化未入变化块 | diff 只比较固定 schema 值 |
| A9 | 稳定 ID、唯一约束、来源与类型渲染 | 连续两周查看是否重复上周条目 | 修 URL/标题稳定 ID 或列表增量逻辑 |

## 8. 上线与每周运行

1. PR 的 `Verify / code` 必须通过；它只跑关键冒烟检查。合入 `main` 或准备部署时，再要求 `Verify / full-regression` 与 `Verify / production-image` 通过。
2. 运行 `npm run production:check -- --file .env`；真实 Feed 合计少于 3 条时不部署周报任务。
3. 备份现有 SQLite volume，部署新镜像；首次启动只有目标数据库不存在时才复制种子。
4. 验证健康、客户档案和行业周报三个地址均返回 200。
5. 配置 GitHub Actions 的 `FIELD_BASE_URL` 与 `FIELD_CRON_SECRET`，后者必须和服务器一致。
6. 手动运行一次周报工作流，确认 HTTP 200、`ok: true` 和 `reportUrl`。
7. 每周由 FDE 打开来源并选择至少 3 条真正有用的信息；系统保存实际选择时间。
8. 每周复查所选记录进入客户档案第 6 章；连续四个自然周达标后才完成 M6。

详细服务器命令、环境变量和回滚边界见 [`production-rollout.md`](production-rollout.md)。

## 9. 变更规则

- schema、来源类型、章节或验收门槛变化时，先更新 `GOAL.md`，再改 SOP 和代码。
- 新采集器必须有真实 fixture、字段级来源测试和失败样本。
- 日常修改只运行与变更相关的检查和 `npm test` 冒烟集；完整 329 项回归与生产镜像留给合入主分支、发布前或手动触发，不为每次文档和小改动重复执行。
- 不允许为通过测试降低来源、页码、同行业、文字或四周时间门槛。
- 生产数据迁移必须向后兼容；已有 `DossierRun` 和 FDE 选择时间不可伪造或覆盖。
- 每次上线后把实际镜像、验证时间、外部依赖和未到期门槛写入验收报告。
